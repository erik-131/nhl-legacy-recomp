# L2 module 3: period length, game clock, period index and rule-type predicates as readable C++

Level L2 of docs/source-replication-study.md, same pattern as docs/l2-penalty.md. Labels: **[read]** = from the disassembly, **[measured]** = observed in the unit test, **[guess]** = not confirmed.
Files: `src/l2/rules.h` (layout constants + API), `src/l2/rules.cpp` (pure functions over an `Env`), `src/l2/rules_hooks.cpp` (guest hooks, cvar `nhl_l2_rules`), `tests/l2_rules/test_rules.cpp` (synthetic data only), CMake: next to `penalty_hooks.cpp` in both source lists. No EA names or maps are in git; function names are our own descriptive labels. Nothing here was run in the game.

## What the game does (summary) [read]
- There is no "number of periods" field. Regulation is hard-wired as period kinds 0, 1, 2; every later period has kind 3 ("overtime"). The kind is `min(period index, 3)`. What happens after period 3 (play OT, end, shootout) is decided by game-flow code that was not found in this pass.
- The game clock is two 16-bit words in the game-data block: virtual seconds left in the period and a sub-second tick counter. A period is always 1200 virtual seconds (20:00), except an OT period (kind 3) in rulesets 2, 3, 4, 7, which is 300 (5:00). The clock is (re)initialised by `InitPeriodClock` when a period starts.
- The *speed* of the clock is separate: each virtual second lasts `rate` ticks, and `rate` is normally the rules value "period length" N (rules+72). So "a 5 minute period" means the same 20:00 clock running at N=5 ticks per second [read], the finding in docs/rule-hooks.md. Special cases in the rate function: below 10 s left, and in the last minute of period 3 and OT, the rate is 29 (slower clock) [read]. Real seconds per virtual second = rate / tick frequency; the tick frequency (30 or 60 Hz) was not confirmed [guess].
- The "overtime type", "shootout" options and similar are values in the rules struct that the game reads in many places (175 functions load the rules pointer). Two fields are understood: rules+36 (ruleset selector, drives OT format and OT length) and rules+56 (a 0..5 enum read by seven tiny predicates). Which rules key names map to which offset needs the descriptor at 0x8316AAB8 plus the image strings (not available in this session) [open].

## Layout [read]
All big-endian. Game-data block at guest VA `0x83C87508` (same block as docs/l2-penalty.md).

## What a custom-mode module would hook
1. **Custom period length (minutes).** Two independent knobs. (a) Clock *speed*: rules+72 (what `nhl_period_length` writes) or, more robustly, the rate function 0x83480C10 (return N directly, keep the 29 special cases or drop them). (b) Clock *length*: `PeriodLength` (0x83475D50) is the single source of truth for the 1200 / 300 seconds; hook it to return any number of seconds (kind and ruleset are inputs). All clock initialisation, the elapsed/remaining time functions and the "clock has started" test go through it, so one hook gives a consistent N-minute period with a normal-speed clock (e.g. return N*60, leave the rate alone). Caveat: ElapsedGameSeconds and 0x8335EDC0 sum `PeriodLength` for the past periods differently (the former uses a fixed 1200); with a custom length use the replace mode so that both agree, or hook ElapsedGameSeconds too. Things that assume 1200 (60-second warning at clock 60, the "clock < 120/60/10" rate special cases, 0x8337FF90) are in absolute seconds, so they still trigger at 1:00 left even in a 3-minute period.
2. **Custom overtime length / format.** OT length is `PeriodLength(3)`; the OT skater format is chosen in 0x8331F540 / 0x8331EDB8 by the ruleset (rules+36) with the RuleGate and OvertimeReduce from docs/l2-penalty.md. A module that wants, for example, a 10-minute 3on3 OT overrides PeriodLength(kind 3) and sets rules+36 to 3 (reduces 5v5 -> 4v4 -> 3v3 through OvertimeReduce) before the OT starts.
3. **Number of regulation periods.** Not a data field: kinds 0..2 are fixed. The branch that moves from period 3 to OT or the end screen was not found (candidates: callers of NextPeriod / SetPeriodIndex, i.e. the transition 0x8339B0C8 and its caller; look for compares of the period index with 2 / 3 near the end-of-period event). A 2-period or 4-period mode needs that function plus PeriodLength for the kind, because kind 3 would otherwise mean "overtime" (short in rulesets 2/3/4/7). Not yet understood.
4. **Shootout on/off, OT type.** The rules struct holds them (descriptor 0x8316AAB8 lists the keys with their field offsets), rules+56 is one enum (RuleTypeIs predicates are the readers; hooking the seven predicates is the cheapest way to flip behaviour without finding all readers). Mapping of key name -> offset needs the image strings; do that with a reader that maps the memory-layout image (offset = VA - base) against the descriptor, outside git.
5. **Hook points in order of leverage:** PeriodLength (0x83475D50), the rate function (0x83480C10), the seven RuleTypeIs predicates, SetPeriodIndex (0x833FB500; clamp or remap the kind, e.g. keep kind 3 for periods >= N), then the game-flow function behind the transition (unknown).

## Verification
`nhl_l2_rules` (env `REX_NHL_L2_RULES`): 0 off (default, pure passthrough), 1 verify, 2 replace. Covered by hooks: ActiveFlag, PeriodLength, InitPeriodClock, SetClock, SetPeriodIndex, ClockBelowPeriodStart, ElapsedGameSeconds, ScaleByPeriodLength (rate flag from the original 0x834859A8), the seven RuleTypeIs predicates. Verify: the readable code runs first against a shadow overlay (reads real memory, buffers writes), then the original, then buffered writes and return values are compared; a difference logs `[nhl-l2] MISMATCH <fn> ...` (first 25 per function), and once a second `[nhl-l2] rules mode=.. calls/mismatches: ...`. Limitation as in l2-penalty.md: writes the original makes that the readable version does not make are not detected. Replace: the OT notifier and (for the tick, if ever used) the rate go through the original guest functions. `nhl_period_length` still works (it writes rules+72, both versions read it).
